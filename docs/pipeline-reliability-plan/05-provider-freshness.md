## Required behavior

1. **Persist per-provider provenance.** For relevant movie/provider identities, record last attempted time, last successful validated retrieval/check, outcome/reason, and enough source identity/version information to explain the values currently stored. Distinguish a provider attempt from a value actually refreshed. Use UTC timestamps and explicit semantics; do not invent success timestamps for legacy data with unknown provenance.
2. **A small useful outcome vocabulary.** Cover successful usable data, verified listing with no usable score, no listing/not in dataset, identity mismatch/ambiguity, blocked/rate limited, transient request/deadline failure, and parse/schema failure. Manual skip/not attempted should be represented without pretending the provider was contacted. Keep reasons machine-readable and bounded; omit secrets, query-string API keys, and raw HTML from persisted records. Existing optional artifacts may hold sanitized supporting detail.
3. **Freshness belongs to the data being described.** Record whether displayed values are newly refreshed, retained from a prior verified observation, unverified legacy values, or cleared by existing solo policy. A failed attempt advances the last-attempt record but must not make old values appear fresh or erase the last known successful observation. A successful HTTP fetch alone is not a successful rating refresh: require usable validated fields under the current parser/selection policy. Do not introduce a stricter identity policy as a freshness prerequisite. If only one of several score/count fields refreshed, metadata must not imply all fields did.
4. **TMDB cache reuse is not another provider request.** A successful shared response may be applied to multiple rows/categories. Record its original observation time/provenance, not a fictitious network attempt per consumer. Preserve request-shape keys and failed-result eviction. Retrieval, cache reuse, and value application may be separate internal events without expanding the public UI.
5. **IMDb freshness is dataset-specific.** Capture validated dataset identity and relevant ETag/Last-Modified/check time separately from per-title rating availability. A verified 304 may advance the dataset's last checked time but does not prove the publisher updated ratings at that time. IDs absent from the dataset have no rating; record that normal outcome without fabricating one. Provider/download failures must not be reported as “ID absent.” Keep writable-temp failures diagnosable without erasing prior ratings in normal Update.
6. **Preserve update behavior exactly.** Normal Update keeps prior values on unavailable providers. Solo Update retains its existing clearing rules and resets `solo_update` only according to established processing/persistence behavior; do not turn this task into endless auto-retry of selected rows. Preserve PR #166's zero-value behavior and existing matching policy; PR #166 did not establish a proven-identity-mismatch policy. Tests must distinguish a row intentionally skipped from an unexpected row exception and from a failed required database write while preserving the existing overall success policy for ordinary row skips.
7. **Integrate with atomic publication, without adding ownership generations.** Persist provider values and their current provenance consistently through PR 4's publication/patch mechanism. Values and the metadata describing those values must commit or roll back together in the appropriate category publication/Update patch. Keep staged observations private until their values commit; do not advance a public revision separately for each provider response. Preserve the last successful observation when a later attempt fails; a failed attempt must not make retained values appear freshly verified. Do not add stale-worker ownership generations, concurrent-writer merge logic, or overlapping-run fencing; the existing run lock is the pipeline coordination contract. For attempts that never publish values, define whether a separate attempt record is retained and ensure it cannot falsely describe live values as refreshed.
8. **Diagnostics without a new run status.** Extend existing summaries with useful provider/reason counts and bounded examples, without creating a new completion classification. Make it possible to inspect “why is this rating old or missing?” using a documented query or existing artifact. Avoid a new dashboard/frontend feature unless strictly necessary for schema compatibility.
9. **Freshness rules are explicit.** Document when a response can be reused during a run and when manual/solo refresh fetches again. Do not silently reduce existing refresh frequency using a new multi-day TTL. If a cross-run TTL is introduced for a demonstrated need, document it, give force-refresh a clear bypass, and never negative-cache transient failures as durable no-listing decisions. Default to the existing refresh cadence.
10. **Bound operational cost.** Use compact indexed records/batched writes or equivalent. Avoid one extra blocking request per provider per title. Bound any attempt history and document retention. Do not expose internal diagnostics or privileged write functions to public frontend roles.
