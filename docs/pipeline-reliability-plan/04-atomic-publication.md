## Required behavior

1. **Specify the publication unit.** Prepare the selected category's ready changes privately and publish them together once. Now Playing, Coming Soon, and Cinematheques remain independent categories. Aggregate the prepared affected cinema snapshots and coupled final movie/screening data, plus derived preview data where present. A normal run selecting mapping and Update must not publish intermediate mapper rows and then visibly apply Update rows one by one. Stage the selected category's relevant cleanup/map/Update changes before the final commit. A failed cinema scrape retains its old rows; it need not prevent other eligible snapshots from participating in the category publication under existing failure semantics. Coming Soon has its own coupled data. Independent categories may publish independently; a failed optional rating is not a reason to hold valid screenings. Do not introduce a whole-run all-categories-success requirement. Document exactly what atomicity covers and what remains independent.
2. **Prepare privately; commit together.** Complete network enrichment and validation before the short commit operation. Prefer staged data plus one database transaction/function that validates readiness, applies related final rows and safe deletions, maintains required movie-code/preview invariants, advances the publication revision, and records publication completion/raw processing state together. An equivalent versioned-dataset design is acceptable if it also handles all readers/writers. Separate REST upserts with compensation are not atomic. Do not hold database locks while doing HTTP scraping/enrichment.
3. **Preserve valid old state on failure.** Failure at any point before/during commit leaves the previously published unit intact. A non-ready staging set cannot replace live data. Optional missing metadata must not invalidate otherwise publishable rows. Apply PR 3's actual full-snapshot replacement rule: only the latest source attempt that is complete and row-count matched may publish; for an eligible Now Playing/Cinematheques snapshot, publish resolved rows and delete prior screenings absent from those rows, even when another raw title is unresolved. Leave unresolved raw rows unmarked for a later normal matching attempt. A failed, running, missing, or count-mismatched latest attempt cannot authorize deletion based on an older snapshot. Explicit skips remain legitimate outcomes. Reconcile prerequisite movie rows before exposing their screenings, without assuming an old early `added` flag is reliable.
4. **Idempotent commit and unknown outcomes.** Give a publication a stable identity and payload/input fingerprint. A lost HTTP response after commit must be resolved by querying that identity and returning the existing committed result, not replaying destructive work. Reject reuse of an ID with different content. Match decisions, prepared state, and committed state must remain distinct.
5. **Validate the publication input under the transaction.** Recheck that the prepared source snapshot is still the latest source attempt for its cinema, is complete with a matching row count, and has the same input fingerprint before applying the commit. Keep the existing run lock as the whole-run coordination mechanism. Do not add per-cinema ownership generations, stale-owner RPCs, overlapping-run fencing, or a second run-coordination system. Stable publication identity/fingerprint and lost-response reconciliation remain required for idempotent commits. Handle PR 2 termination/deadline without claiming that killing a client rolls back a database operation already in flight; put reasonable lock/statement bounds on commit operations.
6. **Application read consistency is a separate requirement.** A transaction prevents partially committed database state, but separate HTTP reads can straddle commits. Implement a practical supported read protocol: immutable revision-pinned datasets, a coherent read endpoint, or revision checks with bounded discard/reload and cache-generation handling. Integrate catalog, showtime range/pagination, preview data, movie-code lookups, and ticket availability where their consistency depends on the publication. Merely adding an active pointer or keying each independent request to whatever revision is current is insufficient. Read each API/preview response coherently and label it with the revision actually read, not a later revision fetched after its queries. Cache headers, CDN responses, client caches, and revision metadata must describe the same payload. Define category revision scope for shared movie-code and cross-category reads.
7. **Handle existing cached data.** A catalog from revision A and newly fetched showtimes from B cannot be silently merged into one coherent result. Ensure query keys, pagination, range coverage, cancellation, and invalidation respect the chosen revision boundary. Bound retries during frequent publications; retain an internally consistent result or surface the existing ordinary load-error behavior rather than loop forever. Preserve frontend URLs, movie codes, filters, and current UX.
8. **Bring other writers into the contract.** Normal/solo Update, relevant admin edits, cleanup/dedupe, preview generation, and realtime-triggered work must not mutate coupled live state invisibly outside the chosen publication/read protocol. Use narrow integration rather than reimplementing each feature. Avoid realtime loops caused by metadata/commit bookkeeping. Preserve manual edit precedence. Do not add cross-run ownership generations to handle overlapping pipeline runs; the existing run lock is the coordination contract. Document how Update-only runs privately prepare the selected category patch and commit it without requiring unselected scrape/mapping stages. Preserve the existing selected-row scope for realtime solo Update while committing its values, reset flag, and revision consistently. Avoid holding the entire run until unrelated categories finish.
9. **Side effects follow committed state.** Ticket alerts may inspect only committed now-playing data. Staging and rolled-back publication cannot trigger a real send. Preserve the existing subscription delivery ID and provider idempotency design; do not put email delivery inside the database transaction or replay it with publication retries. Test the commit-to-alert handoff with a fake sender and normal expected skips.
10. **Controlled migrations and rollout.** Use additive migrations with explicit privileges/RLS, constrained function execution, and safe search paths where needed. Staging/checkpoints are not public write APIs. Preserve permanent movie-code assignments. Provide bootstrap/backfill, backend/frontend rollout order, abandoned-stage cleanup, and a rollback procedure that cannot expose half a publication. If versioned data is retained, garbage collection must respect readers still using older revisions. Do not silently fall back to unsafe multi-table writes when schema is missing. Keep legacy raw rows without manifests processable through an atomic non-authoritative publication path, with no stale deletion from legacy input; do not manufacture scrape completeness. Reconcile pre-PR4 partial checkpoints/live orphan states during upgrade without requiring a production flag reset or destructive rescrape. Generate new migration versions after the latest actual repository/hosted history, currently `20261020114942`; do not edit already-applied migrations.
