# Pipeline reliability handoff

Updated 21 October 2026 for PR4 on main through PR #174. PR3 is merged; PR4 adds atomic category publication and revision-aware readers. PR #164, PR #166, and PR #168 remain the dataflow foundation. The PR3 sections below describe the input/checkpoint contract that PR4 preserves.

## Current guarantees and limits

PR #164 owns shared stages, the run-scoped successful TMDb request cache, request coalescing, Update prefetch, Update worker limits, and union IMDb projection. PR3 reuses those paths; it does not add a parallel cache or scheduler. PR #166 owns the current matching and parsing policy, and PR #168 owns whole-run deadlines and process cleanup.

Expected skips, ambiguous records, and unavailable listings remain normal successful run behavior. PR3 adds no “completed with skipped rows” status, warning exit code, or skip threshold. Existing normal Update retention, solo Update clearing, title grouping, alias handling, stable movie codes, and notification behavior remain in place.

PR3 records source completion and makes all three category publications resumable at confirmed write phases. It does not save TMDb match decisions: an interrupted or unresolved title is searched again on the next normal pipeline invocation. PR3 does not schedule that invocation. A complete now-playing or Cinematheque snapshot replaces that cinema’s prior screening set: screenings absent from the successfully resolved new snapshot are deleted even if another row in that snapshot is unresolved. Unresolved raw rows stay unmarked for a later matching attempt. PR3 alone left related writes non-atomic. PR4 now prepares these writes privately and commits the category and publication marker together.

## Matching retries

TMDb searches continue to use the existing grouping, title fixes, aliases, skips, and candidate selection. PR3 does not persist matched IDs, intentional skips, or provider failures across runs. If a request raises an error, the dataflow exits with publication unfinished and the raw row unmarked; the existing runner retries that failed dataflow up to three attempts in the same run. If all attempts fail, a later normal run can claim the unfinished snapshot and match again. A successful search with no usable candidate is an expected unresolved row rather than a run error, so it stays unmarked and is searched again on the next normal run.

PR3 adds no retry scheduler. After the existing three attempts are exhausted, another attempt depends on the existing runner being invoked again, either by its current schedule or manually. Existing request-level retry limits remain separate from whole-dataflow retries.

## Scrape manifests and empty results

`pipeline_scrape_snapshots` records one UUID-scoped attempt for a source table and cinema. `BaseCinema.scrape()` inserts a `running` manifest before navigation, attaches the UUID to that attempt's raw rows, and marks the manifest `complete` only after raw upload succeeds. Exceptions mark it `failed` when the manifest exists. `row_count` is the number of raw rows for that snapshot; it is reconciled after the existing raw-row dedupe and age cleanup remove rows later.

An empty scraper result is not automatically success. `formatAndUpload()` raises on an empty gathering table unless the scraper calls `confirmEmptySnapshot()` with positive source evidence. The Jerusalem Cinematheque scraper does this only after all 45 calendar dates explicitly show the source's no-screenings state. Other scrapers currently treat an empty page as incomplete unless they add similarly verifiable evidence. This can retain old future screenings until that source has an authoritative complete snapshot; it avoids interpreting a blocked or half-loaded page as “nothing is showing.”

The dataflow first selects the latest attempt for each table/cinema, regardless of status. It processes that attempt only when its status is complete and its manifest row count exactly equals the raw rows associated with its UUID. A newer failed, running, or count-mismatched attempt fences off an older complete snapshot; none can authorize stale-row deletion. A confirmed complete snapshot with zero rows is still a real scope and may remove stale screenings for that cinema. Old rows with no manifest remain processable only through the legacy path; legacy input can be marked after successful publication but cannot authorize stale-row deletion.

Raw dedupe keys include `snapshot_id` for new attempts, so two retries or later snapshots are not merged before the dataflow reads them. Rows without a snapshot UUID retain their prior dedupe grouping. When existing raw dedupe or age cleanup deletes rows from a complete snapshot, it updates that manifest's count so the next read can validate the remaining snapshot exactly.

Coming-soon mapping uses the same latest-complete/legacy-unadded selection so failed source attempts do not feed matching. It does not delete final coming-soon rows based on an empty scrape.

## Publication checkpoints and resume behavior

`pipeline_publication_checkpoints` is keyed by `(category, snapshot_id)`. It stores the snapshot input fingerprint, publication phase, and whether any identity work was unresolved; it does not cache a TMDb match. There are no per-cinema owner tokens or generations in this PR. Claiming requires that the snapshot is still the latest complete attempt for that cinema. A published snapshot with the same fingerprint and no unresolved groups is skipped; changed evidence or unresolved results are matched again on a later normal invocation.

The current phases are `prepared`, `screenings_written`, `movies_written`, `stale_rows_deleted`, and `published`. Coming-soon snapshots use the movie-write phase for the `finalSoons` upsert and have no screening deletion. If a multi-table write fails, a retry with unchanged, resolved evidence resumes after the last confirmed phase. If matching had unresolved identities, the retry starts matching again because provider results may have changed. Raw rows are marked only after the relevant final-table writes succeed. PR4 keeps intermediate phases private and commits only the completed result. Existing unfinished PR3 phases are still accepted as migration inputs.

Each `PreparedPublication` records category, snapshot UUID, run ID, fingerprint, screening and movie rows, stale and retained screening IDs, raw IDs eligible to mark, unresolved group keys, and whether source coverage is complete. PR4 can consume this representation without changing screening identity or snapshot replacement semantics.

## Retention rules

For a complete now-playing or Cinematheque snapshot, the pipeline builds a plan per cinema. Screening identity remains the existing title-based key: normalized English title, cinema, city, date, time, technology, screening type, original language, and dub language. A new raw database ID on the next scrape does not by itself create another final screening when those fields match. Event links do not override the title key.

The complete snapshot replaces that cinema’s current final-screening set. The pipeline upserts resolved new screenings, then deletes existing screenings whose keys are absent from those resolved rows, including when another title in the snapshot is unresolved. For example, if old final rows are Dune, Barbie, and Spider-Man, and the latest complete scrape resolves Barbie and Spider-Man but cannot match Dune, the new Barbie and Spider-Man rows are published and the old Dune row is removed. The Dune raw row remains unmarked so a later run can search it again. A complete empty snapshot removes all old screenings. Failed, running, missing, or row-count-mismatched snapshots never authorize stale deletion. Existing date-based expiration cleanup remains separate.

## Schema access and deployment

The migration enables RLS and revokes direct table/function access from `public`, `anon`, and `authenticated`; the backend service role is the only granted writer and can call the claim/advance RPCs. The pipeline tables intentionally stay out of `packages/server/src/db/schema.ts`’s `applicationTables`, so the Express runtime cannot query internal checkpoint state; Drizzle maps the nullable `snapshot_id` columns on the three raw tables to preserve physical schema parity. PR3 has no per-cinema publication-ownership generations or checkpoint/snapshot cleanup RPC. Apply `20261020113605_pipeline_publication_checkpoints.sql` before deploying PR3 workers because the code reads and writes the new tables and raw `snapshot_id` columns. The migration is intentionally timestamped after both current main's `20261020065120_better_auth_accounts.sql` and DEV's independently applied catalog-access migration `20261020112925`; verify the pending migration against each deployed history before applying it. Keep the DEV-only catalog-access change separate from this rollout; do not propagate it to Production through PR3. No checkpoint backfill is required: existing raw rows without manifests use the legacy path, and matching runs under the current policy when the pipeline next processes them.

## PR4 implementation and rollout

Each selected category prepares its Clean, TMDb and Update work against a private in-memory workspace. The existing queries, matching policies, provider work, grouping, skips and Update row behavior operate on that workspace. PR #164 still owns the request cache, coalescing, prefetch, IMDb union and worker limits. Categories reserve short codes together within a run so private preparations cannot allocate the same code. Existing codes remain permanent.

After a category's last selected stage succeeds, the worker uploads bounded private JSON parts and invokes `commit_category_publication` once. The transaction validates the upload fingerprint, read inputs, manual fixes/skips, latest complete source attempts and source counts; applies the category's movie/screening/code changes and planned stale deletions; marks eligible raw rows and PR3 checkpoints; records the durable receipt and catalog revision. Any error rolls all these writes back. It uses the existing admin correction advisory-lock namespace in sorted TMDb order. Brief source/helper locks cover validation and commit only, never HTTP/provider work. The lock timeout is five seconds and the write loops enforce a sixty-second commit budget, independently of PR #168's process watchdog.

A failure in a selected stage prevents that category's publication and ticket dispatch. Other categories remain independent. Selecting only Update still publishes only that selection. Each realtime solo update and standalone cleanup invocation receives the same transaction boundary; the long-lived watcher remains outside it. Multi-category cleanup commits categories independently. The manual table-copy utility requires an explicit single category. There is no global all-categories transaction, new match cache, new skip-success status or provider freshness policy.

Complete cinema snapshots still replace old screenings with resolved new rows, including removal of old screenings for unresolved titles. Their raw rows remain unmarked for the next normal matching run. Failed/incomplete scrapes cannot authorize replacement. Coming Soon keeps its dated/empty-result rules. Legacy raw rows without manifests and PR3 checkpoints left at intermediate phases are consumed under the existing rules without resetting data or inventing completed scrapes.

The Express/Drizzle repository uses one read-only repeatable-read transaction for each public catalog, showtime, theater, ticket-availability and Open Graph read. Public responses include `X-Kartiseret-Publication`. A request pinned to an outdated revision returns `409 publication_changed` with `private, no-store`. The browser pins dependent requests to its catalog revision, separates showtime and ticket cache keys by revision, refreshes loaded catalogs on 409 and rejects delayed responses from old revisions. Catalog responses and the browser request path disable HTTP caching so an intermediary cannot repeatedly supply an old catalog during recovery. Revision-pinned showtime and availability responses also use no-store; unpinned independent public ranges keep their existing HTTP cache policy. Existing direct admin writes advance the same revision transactionally. No browser Supabase access or private API/security change is introduced.

Ticket-alert delivery starts after the selected now-playing category commits. It continues using the existing delivery idempotency keys and authenticated internal recipient API. There are no email or recipient lookups inside the publication SQL transaction.

Apply `20261021044037_atomic_category_publication.sql` after current main's migrations, before deploying the PR4 API or workers. It adds private publication headers/parts, private SQL helpers, the service-role-only commit/prune RPCs, and a revision table readable by the API runtime. Explicit grants are required because PR #174 revoked future default Data API exposure. Existing PR3 migrations and data stay intact. Pause scheduled/manual workers and the solo watcher during the code transition so old workers cannot perform phased publication after deployment; resume them only on PR4 code. Deploy the API before the browser code that requires its revision header. This PR does not apply hosted migrations, deploy services, start a live job or send real email.

For an interrupted/unknown commit, use the nonsecret artifact `backend/utils/log/logger_artifacts/<run_id>/publication_<category>.json` to find `pipeline_publications.publication_id` and verify its fingerprint. An `applied` receipt means the entire category committed, even if the RPC response was lost; the same ID/fingerprint returns that receipt without repeating writes. `prepared` means no successful publication has been recorded; after confirming the worker/request has ended, an ordinary later run prepares from current live state. An unavailable receipt lookup remains an error, not permission to assume rollback. Applied receipts are retained, while their large parts are deleted in the successful transaction. Operators may call the service-only `prune_abandoned_publications()` to remove at most 100 preparations older than 30 days whose run is no longer active; no cleanup scheduler is added.

PR5 remains provider freshness/failure metadata. It should add that metadata to this workspace/transaction and API read boundary, without reinstating matching changes, durable match caching, event-link identity, unresolved-cinema protection, run ownership generations or another efficiency project.
