# Backend overhaul architecture decisions

## PR 1: workspace and contract boundaries

- The repository root owns the npm workspaces and the only npm lockfile. Workspaces are `packages/contracts`, `packages/server`, and the existing `Codebase - Kartiseret Web` folder. Python, Supabase SQL, and Vercel API paths remain in place.
- `@kartiseret/contracts` emits ESM and TypeScript declarations into ignored `dist/` output. Its explicit exports are `runtime`, `movies`, `showtime-day`, `showtime-filters`, `showtime-links`, and `preferences`; there is no browser-wide barrel.
- Shared contracts use Zod and pure helpers only. They have no browser globals, provider clients, server dependencies, UI state, or secrets.
- Root scripts build contracts before server and frontend consumers. Vercel builds the SPA, Express API adapter, and fixed Open Graph handlers from the root lockfile.

## PR 2: Express, SQL baseline, and Drizzle

- `@kartiseret/server` owns the side-effect-free Express app, server-only environment parsing, normalized catalog mapping, database composition, and API tests. `createApp` receives a repository and never opens a socket or reads environment variables.
- The server uses stable `drizzle-orm` with `drizzle-orm/node-postgres` and the existing `pg` driver. Its explicit `pg.Pool` has a configurable maximum (default 1 for the Vercel serverless runtime), finite connection and idle timeouts, remote TLS verification (including the configured Supabase CA for Supabase PostgreSQL hosts), and an idempotent `close()` lifecycle. A warm Vercel instance reuses its pool.
- `src/db/schema.ts` maps all 18 public application tables, preserving physical names, column types, nullability, defaults and keys. It is a query mapping only. Provider-owned `auth.users` foreign keys, RLS, grants, checks, indexes, publication membership, and all DDL remain owned by Supabase SQL.
- Timestamped SQL under `supabase/migrations/` is the only schema/migration authority. The current-state baseline bootstraps a new empty project once; it is never replayed against existing DEV or production. Drizzle Kit is not part of install/build/start and is not used to apply DDL.
- The runtime role inherits read access only to `finalMovies` and `movieCodes` for this first API slice. Migration/admin access stays separate. The Express endpoint uses that restricted identity; `createApp` unit tests inject repositories without a database.
- Express exposes `GET /api/v1/health` and `GET /api/v1/catalog/now-playing` as the first stable API slice. It preserves pending-row exclusion, `popularity DESC NULLS LAST`, numeric movie-ID tie ordering, bounded movie-code reads, DTO normalization and safe JSON errors. Public browser reads and existing Open Graph handlers remain unchanged until PR 3.
- `api/dispatch.ts` is the explicit Vercel function for API and OG requests. `vercel.json` rewrites `/api/*` and short links to it before the SPA fallback; it restores the original API path before calling Express and dispatches OG paths to the existing handlers. Vite's `/api` proxy is optional through `VITE_API_PROXY_TARGET`.
- Ordinary `npm run verify` remains database-free. GitHub Actions runs the guarded, disposable PostgreSQL 17 bootstrap and Drizzle integration suite separately. The bootstrap accepts only local `kartiseret_test`; it never falls back to a hosted URL.

## PR 3: public reads, browser transport, and social previews

- `DrizzleCatalogRepository` also implements `PublicDataRepository`. All public movie catalogs, permanent-code lookup, bounded showtime ranges, all-city ticket availability, and theater/city projections go through Express and Drizzle. Public response schemas live in `@kartiseret/contracts/public-data`; the browser does not import Drizzle or query public application tables through Supabase.
- The public routes are `GET /api/v1/catalog/now-playing`, `GET /api/v1/catalog/coming-soon`, `GET /api/v1/showtimes`, `GET /api/v1/theaters`, and `GET /api/v1/ticket-availability`. Every response uses `{ data, error }`; failures use a safe `{ data: null, error: { code, message } }` envelope. The catalog DTO includes each movie's permanent code and a settled `movieCodesStatus` (`ready` or `failed`). Movie-code reads are batched, use string-safe IDs, and do not invent a foreign key between `bigint` and integer columns.
- Showtime queries require a real ISO date, an inclusive 1–180 day range, a nonempty city, and an optional PostgreSQL-integer movie ID. Date values remain calendar strings and `time without time zone` remains a local clock string; no timezone conversion is performed. Incomplete legacy rows are omitted as they were by the former browser mapper, while malformed nonblank values fail as data-integrity errors. Public links are normalized to HTTP(S) or `null`; availability candidates with neither valid language link are omitted.
- The theater query uses the actual `theaters.city_name → cities.name` relationship with a full join so cities without theaters remain visible and a broken join is distinguishable from an empty theater list. Invalid city map metadata produces an explicit data-integrity error rather than fabricated coordinates.
- TanStack Query still owns query keys, freshness, cancellation, deduplication, broad/targeted showtime coverage, incremental ranges, targeted movie prefetch, and cache replacement. A small same-origin fetch client validates JSON with shared Zod schemas and passes `AbortSignal`. The browser does not issue a second movie-code request or use a hidden Supabase fallback when code lookup fails.
- Ticket availability is an independent all-city API query. Preferred-city choice, expiry/grace behavior, and encoded share paths remain in the frontend domain helpers. Protected preference storage, admin membership/edit calls, and account subscription list/create/cancel calls remain direct Supabase operations for PR 4.
- OG HTML and image handlers now call the public Drizzle service directly; they do not issue an HTTP request back to the deployment or instantiate a browser Supabase client. Sharp and its rendering code stay in the web server-only tree. `vercel.json` includes the server/contracts build outputs, static SPA HTML, and OG image assets used by the functions.
- Forward migration `20261015162250_public_api_runtime_select.sql` grants only `SELECT` on `finalSoons`, `finalShowtimes`, `cities`, and `theaters` to `kartiseret_runtime`, with table-specific RLS policies. The baseline already has equivalent `TO PUBLIC` read policies on those tables. Supabase's advisor flagged the duplicate runtime policies, so `20261016040826_remove_redundant_public_read_policies.sql` removes only those four duplicates while retaining the grants and baseline policies. Private preferences/subscriptions and all writes remain unavailable to the runtime role. The disposable PostgreSQL bootstrap replays every active timestamped SQL migration in order.
- DEV is `Kartiseret - dev` (`jbydpmjjptwevyijarzl`); production was not touched. The public-read migration is in DEV's ledger as `20261015162250`. The duplicate-policy cleanup was applied directly with Supabase SQL after repeated `apply_migration` calls expired before returning; its final state is verified, but the provider migration ledger has not yet recorded the cleanup version. Reconcile the DEV migration ledger with the checked-in version before the next provider-managed migration push.
- CI's PostgreSQL 17 job runs the real-role API integration suite and Chromium Playwright browser scenarios after the ordinary frontend/server checks. `npm run web:og:smoke` runs built OG handlers from the repository-root working directory and checks the built SPA fallback, actual JPEG output, Sharp image sizing, guarded remote-image fallback, fonts, and Vercel asset inclusion.
- Root `web:build` and `web:typecheck` build the server workspace before checking the web workspace, because the web server-only OG modules import the server package through its built exports. This keeps clean-checkout verification independent of stale ignored `dist` output.

## Schema inventory and native type conventions

`applicationTables` in `packages/server/src/db/schema.ts` accounts for all 18 physical tables. `date` values are strings, `time without time zone` values are local clock strings, `timestamptz` values are instants, and `utilRunLogs.date_created` remains a timezone-free Jerusalem wall-clock string. The pool overrides only PostgreSQL timestamp-without-time-zone parsing to keep that wall clock as text. PostgreSQL `bigint` values use JavaScript `bigint`; `numeric` ratings remain exact decimal strings under node-postgres. Nullable arrays stay nullable, including `finalMovies.genres`.

The mapping does not invent an auth schema. SQL-owned `auth.users` references are documented at their app columns and continue to exist in the SQL baseline. The actual `theaters.city_name → cities.name` relationship and the subscription composite primary key are represented. SQL-only policies, checks, partial indexes and Realtime membership are intentionally not recreated in Drizzle.

## Hosted development and migration lineage

- Hosted DEV is **Kartiseret - dev**, Supabase project ref `jbydpmjjptwevyijarzl`, PostgreSQL 17.11, `eu-central-2`. Production remains separate and was not modified.
- DEV records baseline migration version `20261015141043` with provider display name `20261015122907_current_app_schema_baseline`, followed by PR 3 migration version `20261015162250` named `public_api_runtime_select`. The checked-in filenames and disposable bootstrap use the applied versions. This provider baseline version/name difference is documented; no baseline reapplication is needed.
- Fictional seed rows are used for DEV and disposable CI only. CI never resets hosted DEV or production.
- Vercel Preview uses the restricted DEV runtime `DATABASE_URL` and `DATABASE_SSL_CA_CERT` from the DEV project’s SSL Configuration; migration/admin credentials do not belong in app runtime or browser configuration. Neither the database credential nor certificate value is checked in or logged.
- Remote PostgreSQL connections require verified TLS. The transaction pooler connection and custom shared-pooler username come from Supabase's Connect dialog. The Drizzle node-postgres path does not attach named, session-bound prepared statements; integration against the actual Preview runtime remains a deployment acceptance check.

## Lockfile and dependency scope

The root lockfile is the only npm lock. PR 2 retains the original `pg` dependency and adds stable `drizzle-orm` without an additional driver, schema migration runner, generator, or auth package. Prisma runtime/CLI packages, generated client output, scripts, URL options, install allowances, and dependency-only overrides are removed. Existing `source-map-js`, `sharp`, and `esbuild` resolutions are retained.
