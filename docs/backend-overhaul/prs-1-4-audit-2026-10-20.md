## Findings

### A1 — Low: oversized request bodies return 500 rather than 413

`packages/server/src/app.ts:94` limits JSON to 100 KB. Its error handler explicitly maps malformed JSON but not body-parser's `entity.too.large` error; the latter reaches the generic 500 at line 360. This falls short of the plan's deliberate client-input error/status mapping. The response remains safe and private responses remain no-store; this is not an ownership bypass or a failure of normal saves.

Reproduced locally against the built current-main Express app with Supertest:

| Request | Actual |
| --- | --- |
| Malformed JSON PATCH `/api/v1/preferences` | 400 `invalid_request`, no-store |
| JSON containing a 110,000-character siteColor | 500 `internal_error`, no-store |

Recommended small follow-up: explicitly map the known oversized-body error to 413 in the existing envelope and add a regression assertion for both its status and private cache policy. No additional middleware product or generic error framework is needed.

### A2 — Low: checked-in status documents still describe a pre-release PR4

- `docs/backend-overhaul-master-plan-drizzle.md:5` says Production PR4 release is pending and its current-stage instructions still say implement PR4.
- `docs/backend-overhaul/verification.md:3` and `:52` say Production is PR3 / PR4 is unmerged.
- `docs/backend-overhaul/pr-4-handoff.md` still has its original Production-not-performed release checklist.

The completed 2026-10-20 release record is durable in PR #171's description, and the live database/deployment agree with that record. A fresh PR5 executor relying only on repository files could nevertheless misread the current stage or attempt an already-applied migration. Recommended follow-up: add a dated Production release addendum and current PR5 starting-stage note while retaining historical implementation evidence. A status correction must not rewrite historical evidence as newly rerun tests.

### A3 — Existing cosmetic issue: mobile navigation wraps “Showtimes” mid-word

A fresh 390×844 live Chromium screenshot shows “All / Showtime / s”. `Codebase - Kartiseret Web/src/components/bars/Navbar.css:614` permits `overflow-wrap: anywhere`. None of PRs 1–4 changed any CSS file, so this is not a backend-overhaul styling regression. Navigation still works. It is an optional UI polish item, not an unmet backend stage or an auth migration prerequisite.

## Intentional adaptations / verification limits

- The one-function Vercel dispatcher replaces older suggested adapter paths while retaining API/OG/SPA routing; route names use the actual documented contracts rather than duplicating the plan's examples.
- Browser privilege retirement is a versioned post-deployment operation, separate from the additive migration, so old clients survive database preparation. Both stages are complete in DEV and Production. One signup-initialization marker protects existing choices; no application table was reset.
- Actual admin write branches and Realtime signals were exercised in disposable CI/DEV. Production admin acceptance used authorization/no-op/dialog checks to avoid altering existing catalog data or triggering Python enrichment jobs. No live mail or Selenium/scraper job was run as audit proof.
- Email confirmation/reset delivery, final cookie/session policy, app-owned account FKs and Python canonical recipient replacement belong to PR5. Existing Supabase password-protection warning remains documented in the release record; it was not introduced by these PRs.
- Fresh UI smoke is Chromium desktop/mobile, not exhaustive Safari/Firefox, maps/geolocation/device testing or a pixel-diff audit. The code retains the existing UI/CSS rather than introducing a new design.

## Recommendation

Keep the released PR1–4 architecture as the PR5 base. Close A1 and A2 in a small follow-up so the API edge-case status and repository handoff are clean before the auth cutover. A3 can be separate UI polish. No new database project, credential reset, rescrape, schema rebuild or repeat Production migration is needed.
