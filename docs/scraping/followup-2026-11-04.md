# Full scraper retest — 2026-11-04

This retest ran the complete collection path for all 18 scrapers enabled at the time, forcing Selenium and Requests independently where both implementations exist. The comparison preserves duplicate rows, values, and types; only generated run and snapshot IDs are ignored. Runs are read-only: no database writes, publication, notifications, or production timing-history updates. After the retest, Holon was temporarily disabled in the registry because this network continued to receive a LiteSpeed 403, including on a fresh headless Chrome check.

Times include browser startup or HTTP session setup, discovery, metadata, schedules, parsing, validation, and cleanup. They are per-scraper times, not end-to-end scheduler savings. The latest branch includes `main` through `1f23c597` before these follow-up changes.

## Findings requiring follow-up

### MovieLand showtimes

Both full comparisons completed, but neither matched. Selenium returned 1,438 and then 1,342 rows; Requests returned 1,480 rows in both comparisons. The output differences were Requests-only and covered screenings across multiple dates and locations. The repeat confirms the mismatch is not a single transient row, so Requests stays disabled for this scraper.

### Hot Cinema showtimes

The original Requests collector trusted `MovieEventsDaysFilter`. The live endpoint returned different, incomplete date sets on successive calls, producing 894 missing Selenium rows in one comparison and one missing row in another. The collector now queries every calendar date for all 12 theaters from the frozen scrape date through the end of the following month. It verified all 696 theater/date combinations in these runs and detected days with events omitted by the filter.

Three complete pairs after that correction produced 3,508 vs 3,510 rows (two Requests-only “Not Just Cinema” events), then 3,508/3,508 twice. The corrected route was much faster, but the single complete mismatch fails the exact-parity requirement; the production default is therefore Selenium. The Requests route and coverage tests remain available for further investigation.

### Holon

The live page returned a LiteSpeed “403 Forbidden” page to both Requests and headless Chrome. Selenium consequently had no `.events-results .entry-result` element to read. A fresh headless Chrome page check after the retest again returned `403 Forbidden` with zero calendar elements. This confirms a site access failure, not a selector change that can be safely patched from today’s output. The prior November 2 comparison had a separate one-field ticket URL mismatch (44/45 rows exact), so Requests remains unqualified as well. Holon is temporarily disabled in the registry until it is reachable from this network.

### Cinema City showtimes

Selenium does not call one schedule endpoint. It opens the Wix homepage, follows its “show me more” film cards, opens each movie page, and reads the venue, room, date, and time selectors. A time selector option contains the ticket event ID. The Requests collector queries the same underlying Wix collections (`SyncFeatures`, `SyncPresentations`, and `CityDynamicPage`) directly through the public cloud-data endpoint, using the site-issued anonymous token; it does not require a user login.

The complete no-write pair started with Requests at 14:40 UTC: Requests returned 4,041 rows in 3.03 seconds and Selenium returned 4,036 rows in 374.67 seconds. All 4,036 Selenium rows matched exactly. Requests had five additional records: four `SPA WEEKEND` screenings and a second ticket event for an 11:00 screening already exposed by the page. The page’s 11:00 option used event ID `894045`; the duplicate API record used `894058`. The Requests collector now deduplicates by the selector’s film/location/room/date/time key and keeps the first event ID. A fixture test covers this rule.

All four `SPA WEEKEND` rows were independently confirmed in Selenium’s own `/movie/6458` selectors: 12:45 Nov 5 at Glilot (event `893046`), 10:20 Nov 6 at Glilot Lounge (`893342`), 10:20 Nov 7 at Glilot Lounge (`893653`), and 21:40 Nov 9 at Rishon Letzion (`894406`). The homepage film list omits this title, but its direct movie page and schedule selectors expose the screenings. These are documented as a correctness fix: Requests includes valid source screenings that the old homepage-driven Selenium traversal missed.

On the later Requests rerun, 4,036 rows were returned in 3.08 seconds. Against the earlier Selenium snapshot, 4,032 rows matched exactly; the four Requests-only rows were the verified `SPA WEEKEND` screenings. Four same-day 16:30 rows from the earlier Selenium snapshot were no longer present in the later live schedule, consistent with the source changing during the long comparison. A subsequent reversed-order attempt timed out in Selenium at the location selector after 80.09 seconds; Requests still completed in 3.01 seconds with 4,004 current rows. These time-sensitive captures are kept separate rather than treated as parser mismatches.

The public homepage’s ordinary HTML contains 12 film cards. Selenium’s five “show me more” clicks reveal 69 cards, but those clicks produced no Wix collection query or other movie-data fetch in the observed browser traffic. The full homepage-card discovery source is therefore not exposed as a standalone Requests endpoint in the current site. The schedule collector does not hardcode card or event IDs; it independently discovers the complete film and presentation collections. It is Requests-first (`auto`) in production, so successful Requests runs do not start Chrome; Selenium is reserved for whole-scrape fallback if Requests collection or validation fails.

### Temporal-expiry follow-up — 2026-11-04

The user's warning about same-day showtimes expiring was confirmed and led to a collector correction. In a complete Requests-first pair starting at 17:27 Israel time, Requests returned 4,004 rows in 2.81s; Selenium returned 3,998 in 324.69s. All 3,998 Selenium rows matched. The six Requests-only rows were four independently verified future SPA WEEKEND events and two 17:15 screenings that had already passed when the Requests snapshot began. Wix's collection retained those stale same-day presentation records after the page selector stopped offering them.

Cinema City Requests now compares each presentation's actual `dateTime` with the attempt's frozen Jerusalem-local scrape time and excludes events at or before that instant. It uses `businessDate` unchanged for the output, so after-midnight screenings retain the source's business-day date. Coverage diagnostics count the expired source records, and an empty result can distinguish expired screenings from title-filtered screenings.

A live Requests run at 17:39:11 Israel time returned 3,977 rows in 3.03s from 3,991 source presentations. It accounted for one title-filtered row, one duplicate selector option, and 12 expired records. The captured source records were scheduled at 17:30 or 17:35, confirming that the Wix data collection can lag the browser's available showtimes.

A full reversed pair then ran Selenium first at 17:40:57 and Requests at 17:46:27. Selenium returned 3,982 rows in 330.36s; Requests returned 3,973 in 2.68s. There were 3,968 exact shared rows. All 14 Selenium-only rows were same-day screenings at 17:30–17:45, already past by the later Requests snapshot. Requests again returned the four verified future SPA WEEKEND events. One ticket event (890536, Clayface) changed from 22:50 in the earlier Selenium output to 22:30 in the Requests output; the raw Wix record's `_updatedDate` was 17:45:37, during the long Selenium traversal. This is evidence of a live schedule update within the comparison window, so the two captures are not a stable-state parity pair for that event.
